# Phase 2 데이터 경로 설계

`docs/superpowers/specs/2026-08-07-self-supervised-mitigation-design.md`의
후속이다. 그 문서의 §6.1이 정의한 2단계 — 실제 깜빡이는 영상으로 학습 — 를
실행 가능하게 만드는 것이 이 설계의 범위다.

**절 번호 표기:** 이 문서 안의 절은 `§3`처럼 쓰고, 선행 설계 스펙의 절은
`[설계 스펙 §6.2]`처럼 대괄호로 구분한다. 두 문서 모두 §6·§7이 있어 그냥
쓰면 어느 쪽인지 알 수 없다.

---

## 1. 왜 지금 이것인가

phase 1이 끝났고, 답이 나왔다.

30 epoch를 돌려 합성 검증에서 `soft_area` −52%, `temporal` −59%를 얻었다.
붕괴는 없었다. **손실 설계는 작동한다.** 그러나 그 체크포인트를 Tier 0
기준선이 측정된 실제 클립 3개에 돌리면 **0/3 통과**다. 3 epoch짜리가
1/3이었으니 더 학습한 쪽이 더 나빴다.

원인은 목적함수가 아니라 데이터다. 합성 코퍼스의 `soft_area`는 init이
0.0774 — 프레임의 8%만 flag되는 세계다. 실제 클립의 peak은
0.630 / 0.401 / 0.658이고, `data/raw/real_flicker/`의 17개 클립은 전부
1.000에 도달한다. 모델은 실제 footage가 존재하지 않는 체제에 30 epoch 동안
특화됐다. λ 튜닝이 닿는 곳이 아니다.

이 설계는 그 격차를 메우는 데이터 경로를 만든다.

### 이 설계 이전에 검토하고 폐기한 방향

`docs/PROJECT_STATE.md`는 "마스크 블렌드를 무엇으로 대체할지"를 phase 1
이후 1순위로 지목했다. 근거는 `max_area`가 17/17 클립에서 1.000이므로
`mitigate_frame`의 `(1 - mask)` 보호가 무력하다는 것이었다. **측정으로
반증됐다** — 근거와 측정값은 §9에 있다. 결론만 적으면:

- 마스크가 사실상 전면인 프레임은 wonbon 674개 중 5개(0.7%), Cera 234개 중
  0개다. `max_area`는 1초 윈도의 클립 전체 최댓값이라 "가장 심했던 한
  순간"을 말할 뿐, 프레임별 마스크 포화율이 아니다.
- 블렌드가 보정을 가둔다는 가설도 틀렸다. 보정 전 flagged 픽셀
  2,356만 개(wonbon) / 1,118만 개(Cera) 중 마스크 밖에 있던 것은 **0개**다.
  `compute_prior`가 `mask_i = OR(최근 raw 마스크들)`로 만들기 때문에 마스크는
  항상 현재 flagged 픽셀의 상위집합이다. 구조적으로 그렇다.
- 살아남은 깜빡임의 88%(wonbon) / 95%(Cera)는 모델이 편집할 수 있었던 영역
  **안**에 있다. 손이 묶인 게 아니라 고치다 만 것이다.

즉 주된 막힘은 마스크 안에서 충분히 못 고치는 것이고, 그것이 데이터 문제다.

## 2. 결정 사항

| | 결정 | 근거 |
|---|---|---|
| 초기값 | `--init-from`을 만들고 **사전학습 유/무 둘 다 실험** | 합성만 더 하면 나빠진다는 건 측정됐지만, 사전학습 후 실제로 미세조정했을 때도 나쁘다는 증거는 없다 |
| 해상도 | ingestion에서 **긴 변 512로 다운스케일** | `mitigator/infer.py`의 `_MAX_PROCESSING_DIM`이 이미 512다. 학습과 추론이 같은 공간 주파수를 보게 된다 |
| 코퍼스 | 17개 → **14개** (§3) | 사용 불가·중복·평가 오염 위험 |
| 분할 | train 11 / dev 3, **명시적 목록** | 14개에서 해시는 dev의 난이도 스펙트럼을 통제할 수 없다 |
| 체크포인트 선택 | **주기적 검출기 평가 + 스냅샷** | `val_loss`가 목표를 추적하지 않음이 측정됐다 |
| 워밍업 | 앞 `round(fps)` 프레임을 **학습 중심에서 제외** | 검출기가 프레임 0에 전면 마스크를 만들고 지속성이 전파한다 |

### 두 초기값 실험은 순차로 돌린다

무작위 초기화 쪽을 먼저 돌려 기준선을 세우고, 그다음
`--init-from mitigator/weights/phase1/best.pt`로 같은 설정을 돌린다. 비교는
§6의 선택 지표 — dev 3개의 잔여 위험 구간 총합 — 로 하고, 동점이면 트립
프레임 총합으로 가른다. 두 실험이 같은 dev 세트와 같은 `--eval-every`를
써야 비교가 성립한다.

### 별도 val 분할을 두지 않는다

dev 3개가 손실 검증과 검출기 평가를 겸한다. `val_loss`로 체크포인트를
고르지 않기로 한 이상 별도 val 세트에 데이터를 쓸 이유가 없고, 11개뿐인
학습 코퍼스에서 20%를 더 떼는 비용이 크다. `val_loss`는 발산 감지용 보조
신호로만 남는다.

### 명시적 분할이 기존 철학과 부딪히는 지점

`training/mitigator_dataset.py`의 docstring은 분할이 `clip_id` 해시이고
"입력의 순수 함수라 스캔 순서에 의존하지 않으며 동기화할 파일이 필요
없다"고 적는다. 합성 188샘플에서는 옳았다.

14개에서는 아니다. dev는 난이도 스펙트럼을 걸쳐야 하는데([설계 스펙 §6.2]가 eval 6개를
고를 때 쓴 바로 그 기준) 해시는 그걸 못 하고, 14개를 80/20으로 해시했을 때
몇 대 몇이 나오는지도 돌려봐야 안다. 통제력을 택하고, 그 대가인 "동기화할
파일"의 위험은 §7의 양방향 검사로 갚는다.

두 Travis Scott 클립은 제목이 MetLife Stadium과 London으로 다르고 해상도도

## 4. 구성 요소

**새로 만드는 것 하나**

`scripts/ingest_real_clips.py` — mp4 디렉터리를 받아 클립마다 샘플
디렉터리를 만든다. 긴 변 512로 다운스케일, `degraded/000000.png…`와
`meta.json`을 쓴다. 주입은 없다. 기존 샘플은 건너뛰고 `--overwrite`로
강제한다 — 합성 경로의 재개 방식과 같다.

`MitigatorDataset`이 요구하는 것은 `meta.json`의 `fps`와 `degraded/` PNG
시퀀스뿐이고 `clean/`은 이미 불필요하므로, 데이터셋은 이 산출물을 그대로
읽는다.

**고치는 것 둘**

`training/mitigator_dataset.py`
- 앞 `round(fps)` 프레임을 학습 중심 프레임에서 제외
- train/dev 분할을 해시가 아니라 명시적 클립 목록으로

`training/train_mitigator.py`
- `--init-from PATH` — 가중치만 로드
- `--snapshot-every N` — `epoch_%03d.pt` 보존
- `--eval-every N` — 주기적 검출기 재검증과 그 결과에 의한 `best.pt` 선택

**만들지 않는 것**

역방향 스크리너(`screen_clean_clips.py`의 반대). `PROJECT_STATE`가
"누락 3종"의 하나로 적었지만 지금 필요가 없다 — 17개 클립은 이미 스크리닝
됐고 결과가 `data/raw/real_flicker_screening.json`에 있으며, 통과 0건으로
전부 flagged다. 이 도구는 *앞으로 수집할* 클립을 거를 때 쓸 물건이므로,
실제로 새 클립을 수집할 때 만든다. **누락은 3종이 아니라 2종이다.**

`training/cli.py`에 `--no-injection` 플래그를 붙이는 방식도 택하지 않는다.
그 CLI는 *프로파일 × 패턴 × 주입*을 축으로 만들어져 있어서 주입을 끄면
`--profiles-dir`, `--samples-per-combo`, `--injection-mode`가 전부 무의미해
진다. 샘플 이름(`clip__profile__pattern__000`)부터가 실제 클립에는 의미가
없다.

## 5. 데이터 흐름

### ① Ingestion (한 번)

```bash
python -m scripts.ingest_real_clips \
    --clips-dir data/raw/real_flicker --output data/real --max-dim 512
```

`clip_id`는 **파일명 슬러그 + 원본명 해시 8자**다. 허용 문자
(`[A-Za-z0-9._-]`) 외를 `_`로 접으면 서로 다른 이름이 같은 슬러그가 될 수
있어 해시로 유일성을 보장한다. 원본 파일명은 `meta.json`의 `source`에
보존한다.

이것이 필요한 이유는 코퍼스에 이모지(`🤯💥`), `#`, `!`, 한글, 이중 공백이
섞여 있기 때문이다. 이모지가 든 디렉터리명은 Windows에서 위험하고,
`clip_id`는 train/dev 배정의 키라 안정적이어야 한다.

`meta.json`: `clip_id`, `fps`, `source`, `frames`, `shape`.

### ② Prior 계산 (첫 epoch, 캐시)

`MitigatorDataset`이 샘플마다 `compute_prior`를 돌리고 `prior_cache.npz`에
캐시한다. 기존 경로 그대로이며 스키마 버전 3을 유지한다.

### ③ 학습

train 11 / dev 3. dev는 학습하지 않는다.

### ④ 주기적 검출기 평가 (N epoch마다)

dev 클립을 **한 번에 하나씩** 메모리에 올려 현재 가중치로
`mitigate_segment` → `run_detection`을 돌리고 즉시 해제한다.
`scripts/evaluate_mitigation.py`를 서브프로세스로 부르지 않고 in-process로
간다 — mp4를 쓰고 다시 읽을 이유가 없다.

순차 처리가 필요한 이유는 메모리다. 가장 큰 dev 클립이 634프레임 ×
512×288×3 ≈ 280MB인데 `mitigate_segment`가 `output = list(frames)`로 사본을
하나 더 들고 있어 피크는 그 2배다. 셋을 동시에 올리면 1.7GB가 되고, 이
코드베이스는 이미 한 번 그 방식으로 OOM을 겪었다(`mitigator/infer.py`의
얕은 복사 주석).

### ⑤ 최종 평가 (끝나고 한 번)

홀드아웃 6개에 `scripts/evaluate_mitigation.py`. 그 클립들을 처음이자
마지막으로 보는 시점이다.

## 6. 체크포인트 선택

**1순위** dev 3개 클립의 잔여 위험 구간 총합. 바가 "0개"이므로 이것이 목표
자체다.

**2순위** 룰을 트립한 프레임 총합. 1순위가 정수라 초반에 동점이 잦다.
오늘 wonbon에서 구간이 5→4로 겨우 줄 때 트립 프레임은 574→189로 크게
움직였다 — 이쪽이 훨씬 세밀하다.

**제약** 대비 손실이 그 클립의 Tier 0 기준선을 넘으면 후보에서 제외한다.
판정은 **클립별**이고, dev 3개 중 **하나라도** 넘기면 그 체크포인트는
탈락한다. 평균을 쓰면 한 클립을 뭉갠 대가를 다른 두 클립이 가려준다.

모든 후보가 탈락하면 `best.pt`를 갱신하지 않고, 초과 폭이 가장 작은 후보와
그 수치를 로그에 남긴다. 조용히 제약을 완화하지 않는다 — "제약을 만족하는
체크포인트가 아직 없다"는 것 자체가 읽어야 할 결과다.

제약이 필요한 이유는 구간 수만으로 고르면 **화면을 새까맣게 만드는 모델이
이기기** 때문이다. 어두워짐은 수용하기로 했지만 영상을 파괴하는 데까지
동의한 것은 아니다. 대비 손실은 목적이 아니라 **제약**으로 쓴다: Tier 0보다
비싸면서 통과도 못 하면 GPU도 학습 데이터도 필요 없는 고전 방식에 진다는
[설계 스펙 §7]의 논리 그대로다.

dev 클립의 Tier 0 기준선은 `python -m fallback.cli`로 세 번 돌려 한 번
기록한다.

**Tier 0 기준선을 인용할 때 주의:** −52.8%는 **wonbon**이고 Anyma는
**−6.0%**, Cera Khin은 −48.4%다. `scripts/evaluate_mitigation.py`는 고쳐졌
지만 [설계 스펙 §7]과 `plans/2026-08-07-self-supervised-pipeline.md`에는 −52.8%가 Anyma로
잘못 적혀 있다. 정본은
`specs/2026-08-07-tier0-fallback-measurements.md`의 클립별 표다.

**`--init-from`과 `--resume`은 배타적이다.** 동시 지정은 에러로 막는다.
`--resume`은 옵티마이저와 epoch 카운터까지 복원하므로, phase-1 체크포인트를
복사해 넣고 `--resume`을 주면 `start_epoch = 30`이 되어 `range(30, 30)`이
**0 epoch를 돌고 조용히 성공 종료**한다.

**`--eval-every` 미지정 시** 기존 `val_loss` 선택으로 동작한다. phase 1을
그대로 재현할 수 있어야 하므로 기본 동작은 바꾸지 않는다.

**결과 하나를 명시한다:** 평가가 N epoch마다만 도니 `best.pt`도 N epoch마다만
갱신된다. 그 사이 `latest.pt`는 매 epoch 움직이는데 `best.pt`는 멈춰 있다.
평가 epoch에 그 사실을 출력한다.

**비용:** dev 1,142프레임 기준 보정 ~60초 + 검출 ~90초 ≈ 2.5분. N=5,
epoch가 ~10분이면 +5%다.

## 7. 실패 처리

**모든 텍스트 I/O에 `encoding="utf-8"`을 명시한다.** Windows 기본
인코딩(cp949)에 맡기면 한글·이모지가 든 이 코퍼스에서 반드시 깨진다.
`data/raw/real_flicker_screening.json`을 읽을 때 이미 재현됐다.

원칙은 **조용한 실패를 만들지 않는 것**이다. 이 프로젝트는 이미 두 번
당했다 — `--resume`이 0 epoch를 돌고 성공 종료한 것, 그리고 `val_loss`가
개선되는 동안 실제 판정이 나빠진 것.

| 상황 | 처리 |
|---|---|
| 명시적 분할 목록과 디스크의 `clip_id` 집합이 어긋남 (양방향) | 에러. §2에서 받아들인 "동기화할 파일" 위험의 대가 |
| 클립이 `round(fps) + 3`프레임 미만 | ingestion에서 에러. 워밍업 제외 후 남는 것이 없다 |
| `clip_id` 충돌 | 에러 |
| `--init-from`과 `--resume` 동시 지정 | 에러 |
| `--init-from` 체크포인트의 아키텍처 불일치 | `in_channels`를 명시한 메시지로 감싼다. `9+1+16 → 9+1+1` 변경 때 겪었다 |
| dev 클립 하나의 검출기 평가 실패 | 에러. 건너뛰면 그 epoch의 지표가 다른 epoch와 비교 불가능해지는데 로그로는 알 수 없다 |
| 클립이 학습 예제 0개 기여 | 경고 + 클립명. 기존 `samples_contributing` / `samples_scanned` 계수를 쓴다 |
| 모델 출력이 non-finite | `mitigate_segment`가 이미 원본 프레임으로 폴백한다 (변경 없음) |
| 출력 샘플 디렉터리가 이미 있음 | 건너뜀. `--overwrite`로 강제 |

## 8. 테스트

**선택 로직은 순수 함수로 분리한다.** 이미 계산된 지표 목록을 받아 승자를
돌려주는 형태여야 실제 검출기 없이 단위 테스트할 수 있다. 반드시 고정해야
할 것은 **구간 수는 최소인데 Tier 0 대비 한도를 넘긴 후보가 탈락하는가** —
새까만 화면이 이기는 것을 막는 장치다.

**ingest** — 레이아웃 생성, 슬러그가 결정적이고 ASCII, 충돌 시 다른 id,
기존 샘플 건너뜀, `--overwrite` 재생성, 짧은 클립 에러, 비ASCII 파일명 처리

**dataset** — 앞 `round(fps)` 프레임이 학습 중심으로 나오지 않음, 명시적
분할이 클립을 올바르게 배정, 목록과 디스크가 어긋나면 에러

**train** — `--init-from`이 가중치만 싣고 옵티마이저는 새것이며
`start_epoch`이 0, `--resume` 동시 지정 에러, 스냅샷이 지정한 epoch에 생성

**모델이 얌전해졌다.**

### 마스크 면적 분포

`max_area`(1초 윈도의 클립 전체 최댓값)와 프레임별 마스크 면적은 다른 양이다.

| | wonbon | Cera |
|---|---|---|
| 구간 내 마스크 면적 평균 | 0.351 | 0.554 |
| 마스크 ≥ 0.999인 프레임 | 5 / 674 (0.7%) | 0 / 234 (0%) |

지속성이 마스크를 2.3배 부풀린다 (wonbon 원시 평균 0.119 → 0.277).

### 블렌드가 보정을 가두는가

| | wonbon | Cera |
|---|---|---|
| 보정 **전**, 마스크 밖의 flagged 픽셀 | 0.00% | 0.00% |
| 보정 **후**, 마스크 밖의 flagged 픽셀 | 12.09% | 5.45% |
| flagged 픽셀 총량 | −64.5% | −26.2% |

보정 전 0.00%는 구조적이다 — `mask_i = OR(최근 raw 마스크들) ⊇ raw_i`.

보정 후의 5~12%는 **보정이 만들어낸 새 깜빡임**이다. 프레임 i−1에서 마스크
안이라 보정된 픽셀이 프레임 i에서 마스크 밖이면 원본으로 돌아가고, 그
델타가 임계를 넘으면 새로 flagged된다. wonbon 190번 프레임은 살아남은
flagged 픽셀의 100%가 이렇게 생겼다.

## 10. 이번 범위에서 제외

- **역방향 스크리너** — §4. 새 클립을 실제로 수집할 때 만든다.
- **마스크 블렌드 대체** — §1에서 반증됐다. 하드 경계가 새 깜빡임을 5~12%
  만드는 것은 실재하는 결함이지만, 주된 막힘(88~95%)이 아니다.
- **경계 테이퍼** — 공간축(마스크 가장자리)과 시간축(구간 경계) 모두. 스텝
  크기가 최종 모델이 얼마나 어둡게 하느냐에 비례하므로, 무언가 바를 넘긴
  뒤에 재는 것이 맞다. 3 epoch 출력에서 최악 경계 스텝은 0.0780(wonbon)으로
  그 클립 원본의 p95 프레임간 변화(0.1304)보다 작았고 검출기를 트립시키지도
  않았다.
- **`--lambda-temporal` 재탐색** — phase 2 데이터에서 다시 재야 하지만 이
  설계의 대상이 아니다. 10을 출발점으로 쓴다.
